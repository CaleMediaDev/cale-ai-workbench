# How Cale AI Workbench is put together

This guide is for someone reading the code for the first time. The app has four cooperating parts: a Windows installer, a desktop task list, a persistent task supervisor, and local/cloud model services. They run as separate processes so closing the window does not stop a task or a model download.

```text
Setup.ps1 → Install-Backend.ps1 → installed runtimes, tools, models
                                      ↓
long_tasks.py (window) → projects.db ← long_tasks.py --monitor
       ↓                                      ↓
model_library.py --auto           native_agent.py (new tasks)
       ↓                              legacy Hermes (older tasks)
Ollama model store                         ↓
                                  cloud_ai.py → ChatGPT (opt-in)
                                           ├→ OpenRouter free
                                           └→ local Ollama
```

## Where to start

The donation-job section of `small_training.py` adds an independently opted-in CPU lane for small public-data intent-classifier experiments. It runs only the installed trainer, at most two CPU threads and 300 seconds, from a fixed reviewed CLINC dataset and label policy. The child has its own deadline if the parent exits. The main donation lane offers at most one experiment per hour; other code lanes continue. Existing local donors are not opted into training automatically, and Ollama is unnecessary for CPU training. The SQLite `model_experiments` ledger binds dataset/label/gate policy, Python/dependency versions and trainer source hashes; completed weak or screened results are not retrained across restarts. Failed/interrupted attempts can retry twice after an hour; unique folders preserve partial results. Pending draft publication retries reconcile the original branch/PR without retraining. This novelty ledger is local to one PC, not shared experiment coordination.

CPU worker seconds, candidate counts and provider-reported inference tokens are separate measures. Weak benchmark results stay local. Screened candidates can open a draft PR containing only bounded safe JSON model/evaluation/provenance files under `ModelContributions/<fingerprint>/`; these are outside the runtime manifest. A failed upload preserves the local completed candidate rather than retraining it. Accepted code or model contribution PRs receive one contribution credit using the existing authenticated GitHub author records. Neither a passing public intent benchmark nor accepted contribution credit establishes Cale-routing suitability; candidates remain inactive pending independent review. No private user prompts/files or fetched/generated training scripts are used.

Contributions are a separate GUI-owned service in `donation.py`, with controls in `donation_ui.py`. Sources are individually selected: hardware-eligible streaming local Ollama, strictly free cloud, or account-bound ChatGPT plan usage. The service fetches the public `donation-tasks.json` queue and source blobs at a pinned upstream revision, requests exact edits without model tools, syntax-checks them in memory, and submits only a new branch/draft PR. It never executes generated code or merges changes. Provider receipts and resource totals live in `LongTasks/donations.db`; a context-local observer captures free-router calls without double-counting completions. The database also caches distinct merged donation PRs and GitHub author IDs for the accepted-fixes leaderboard.

Slow yields to foreground work. Medium continuously reviews one area at a time; Full Blast adds two ChatGPT-only lanes and a larger public-source budget. Local/free inference remains single-lane, and local donations wait for heavy GPU music/image work. Both continuous modes discover bounded public production/test pairs beyond the maintainer queue without app-imposed daily/open-draft cutoffs. Transactional revision/job claims prevent simultaneous duplicate reviews and recently unchanged reviews; all lanes share provider cooldowns. Every mode honors Stop, consent, account binding, privacy modes, and setup/update holds. Empty queues retry after a minute; failures back off automatically.

The homepage radio in `radio_station.py` stores prompt stations and its durable queue in SQLite WAL. A command queue keeps music polling and Windows MCI audio playback off Tk's thread. It requests 180-second, audio-only jobs from `music_backend.py`, renders one at a time, buffers two ahead, and repeats the current track on underrun. New renders yield to live user songs and setup/update holds. A bounded UUID-owned cache excludes ordinary song tasks and uploads. Playback starts only on user action.

The Hermes agent itself is an external pinned dependency, installed under the app's `data` directory. Cale AI Workbench adds the task supervisor and tools around it. See `downloads.json` for pinned downloads and `THIRD-PARTY-NOTICES.md` for upstream licenses.

The native `transform_csv` tool performs bounded, declarative cleanup with Python's CSV parser and writes a separate output file. It seeds a read-only hash, row-count, and semantic verifier only when there is no existing user verifier (or when updating its own generated one). The semantic check re-parses source and output with the saved transform rules. A guarded startup route gives the model only this tool for simple new CSV cleanup requests and validates its selected input/output paths before execution. Existing outputs, unsupported operations, restrictive project instructions, and queued follow-ups bypass that route. The task checkpoint keeps bounded row counts from successful CSV operations so their results remain visible after older tool messages leave the model context. Legacy `run_command` verifier calls compare project fingerprints before and after execution so a script cannot pass by modifying the output it is meant to check.

## Tasks and state

The UI inserts user requests into `LongTasks/projects.db`. The monitor handles them through a separate `requests` table, so a button click does not block the window. The original request is saved verbatim in `.local-ai/ORIGINAL-REQUEST-<id>.md`; an oversized brief contributes only its beginning and end to the first worker message, which directs the worker to read the full file in sections. Completed follow-ups are mirrored to `.local-ai/USER-REQUESTS.md` inside the project. A new worker gets only the latest three follow-ups in its first message and must read the full file before planning; the file is rebuilt from SQLite at monitor startup, after each new follow-up, and before each new worker card. Older briefs are compacted only when their appended notes exactly match the queue. The monitor creates an idempotent Hermes board card for each task generation. The worker writes `.local-ai/PLAN.md`, `PROGRESS.md`, and `verify.ps1` inside the project folder. A fresh worker receives a bounded snapshot of the saved plan and latest progress in its board brief, then reads the current files. A turn-budget block rolls into a fresh generation only after the old run exits and its files settle; other block reasons still need user input. The supervisor runs `verify.ps1` in a Windows Job object. Software projects then get a distinct review pass. A verified standalone song with a saved playable file finishes immediately; choosing a favorite take is optional feedback. Older song review cards blocked only on listening preference recover after fresh checks. Successful review reaches `ready_for_review`, where feedback is optional. Failed review verification creates a new generation card with the failure evidence; user feedback after review does the same. Stop and Delete retire the board work but preserve project files. Every cycle processes task requests even when model or gateway startup fails, and one task's retryable error does not prevent later tasks from advancing.

`project_memory.py` creates `.local-ai/memory.sqlite3` when a project is created and initializes it for existing projects at supervisor startup. Its FTS5 index refreshes plan/progress documents during search; the agent can explicitly scan source files when needed. File-backed hits are rechecked against the original file's content hash when searched or opened, so an edited or deleted source cannot surface stale indexed text. Multi-word search tries all terms first and filters weak fallback overlaps, such as an old symbol name sharing one word with its replacement. Separate records capture durable decisions, lessons, app components, and skill recipes. The database and its WAL files stay under `.local-ai`, outside completion fingerprints; project source files remain authoritative. MCP memory tools accept only folders registered in the local project queue.

The UI polls every five seconds. Existing task widgets are updated in place; a widget is created or destroyed only when a task is added or removed. Mouse-wheel scrolling is scoped to the task list, and the canvas keeps its pixel position across ordinary refreshes. Progress percentages are estimates from the saved milestone checklist, not a time estimate. The supervisor hashes project contents before and after independent verification and again before acceptance. A verification script that changes source files must be followed by a fresh check. Legacy metadata-only checksums are accepted only for migration after another real verification pass. Review-card retirement is tracked by generation and current card, so feedback that creates another review makes the supervisor inspect the board again.
Short chat keeps the latest ten messages and searches a local SQLite FTS5 index for up to two relevant older user messages. Existing installations are indexed on first use; later user messages enter through a database trigger. Retrieved messages are labeled as older, possibly outdated context. Assistant replies are not indexed as user facts, and only the local quick-answer path receives this recalled chat context. Individual messages are bounded before inference, so a long conversation does not fill the model window.
Personal contact questions take that local path before any public business lookup. Contact lookup functions also reject pronoun-only and unnamed business references, preventing a question about "my phone number" from searching the public web for a business literally called "my".
Model sizing extracts the original request from the persistent board brief. A simple question can use the fast tier, current facts that need public verification use a middle tier, and build work uses a deeper tier. Tool history can raise the tier as a task grows.
Hermes `scheduled` cards remain active while waiting for their next dispatch. Only blocked, triage, or archived cards require attention; treating scheduled work as blocked would stop a long-running project between worker runs.

`LongTasks/install-progress.json` is read by the UI during first-run setup. The setup supervisor retries explicit installer failures and detects a stale "working" record after the exact installer process has stopped; a live, quiet download is left running. Retries are limited and backed off. The optional downloader writes `LongTasks/optional-model-*.json` in the background, uses a Windows file lock to prevent duplicate automatic runs, and leaves weights in Ollama's model store. It checks Ollama for a usable local model before trusting a saved completion status, and checks physical RAM plus at least 12 GB of extra space on the model store's drive before each pull. A catalog signature makes the app rescan when a release adds or changes model sources. The main model gets a second 64K-context alias that shares its weights, leaving the original full-context alias for larger requests. Creation waits for active project workers to finish and automatically retries afterward. Optional model work stays off the main task screen.

The public `models/recommendations.json` feed can add official Ollama models without a full app release. New entries are bounded to Ollama library sources; after download, a real local function-call probe must pass before routing uses the model. On launch and every five minutes while the desktop is open, `self_update.py` checks GitHub releases, verifies the ZIP's published SHA-256 digest, and installs source changes once tasks are idle. It backs up replaced source in `Updates/backups` and excludes `Projects`, `LongTasks`, `Cloud`, model weights, and runtime folders. The updated router starts from a fresh interpreter after the source swap so cached Python modules from the old version cannot contaminate the new process. The desktop uses a Windows file lock to keep one visible window and focuses that window when launched again.

## Accounts and model routing

Cloud credentials are encrypted for the current Windows user with DPAPI under `Cloud/`; they are never included in the release. The local loopback router requires its own random bearer token. ChatGPT connection and ChatGPT plan use are separate choices. The router only tries that plan after the user enables it and for demanding tasks. Otherwise it ranks installed local models by task size and tool capability; free OpenRouter is a fallback if local inference fails. The list of usable models refreshes as background downloads complete.

The router records provider choice and error categories in `Cloud/routing.jsonl`, not prompts, tool results, or account keys. `cloud_ai.py` exposes an OpenAI-compatible loopback endpoint because Hermes expects chat-completion-shaped messages; `chatgpt_auth.py` translates them to OpenAI Responses API requests when the user opts in. Router replies are checked against the tools offered in that request: unknown tool names, malformed arguments, and missing required calls trigger another model route instead of reaching the task worker.
On a model refusal, the router tries installed derestricted local models. It prefers the small tool-probed model for short requests and the large coding model for deep projects. A model advertised as tool-capable is not promoted from the automatic catalog until it makes a correct local test function call.

See [CONTRIBUTING.md](CONTRIBUTING.md). Keep behavior and safety checks in the relevant module, update the README when user-visible behavior changes, and add each new shipped file to `install-files.json`. The source ZIP and EXE embed the same manifest-defined payload.

## Local security evidence

The pinned `cale-security` wheel is an app-owned toolbox extension. Its catalog is registered lazily, and a missing extension does not disable independent tools. CVE records stay in the local SQLite/FTS store under `Knowledge/CVE`; source and binary reports stay with their task. The bridge binds artifact operations to the current supervisor owner and complete instruction hashes. Model arguments do not supply that authority. Stop/Pause and instruction changes invalidate the analysis.

Ghidra uses an exclusive nonhidden app Temp project while its supplied input copy, fixed exporter and report remain task-owned. Analysis does not execute the supplied program. Product matches, source patterns and decompilation are investigation evidence, not a verified deployed vulnerability.

The distribution carries its readable source and tests. Existing Validation imports those tests, and the self-check basis hashes the actual installed package/Java/test bytes. A direct release wheel URL with SHA-256 is installed by the existing requirements updater before source activation. The runtime manifest stays at 250 entries for older clients. See [package documentation](packages/cale-security/README.md).

Camera capture has a separate local lifecycle. The GUI retains each suspended child before assignment/resume and owns a Windows Job with kill-on-close enabled. The family must be observed empty before replacement; uncertainty retains the exact owner for retry. A bounded legacy scan retires only this installation's exact camera entrypoint with a proven expired owner, while current and unknown owners are preserved. A fatal worker error ends that session before later buffered readiness or preview messages can replace it. Readiness follows the first valid frame.


## Durable continuation and verification ownership

Checked SQLite units remain component evidence. After a queue ends, the worker rebuilds ordinary whole-goal work from current instructions, artifacts and saved checks. Optional observations do not earn completion credit. Read-only check receipts are copied and source-bound before use. Saved browser feedback runs only the fixed host checker under current supervisor ownership; unknown ownership or cleanup defers the slice.

Native schema repairs can retain their earlier request bucket only while the selected model, capacity, configuration and advertised avatar headroom remain current. Transient retries rebuild transport authority and preserve one shared usage clock. This is a request-sizing optimization; real latency and KV-cache savings have not been measured here.

Planning instruction read failures are typed before startup briefing writes. The latest checkpoint survives, and a separate per-project SQLite retry hint backs off from two to thirty seconds. Source changes and implausible clock changes bypass that delay. The hint never supplies permission to act without reading instructions. Pause/Stop remain authoritative. Windows verification timeouts terminate the existing owned Job directly.

Each project retains one checkpoint writer. A general parallel task-team scheduler remains future work. The 1,710-case record is composed from retained runs; five skips and all earlier failures remain explicit. It does not establish real-model app delivery or complete installed-suite success.
