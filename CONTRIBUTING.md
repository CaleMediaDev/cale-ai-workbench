# Contributing

The goal is a Windows assistant that a nontechnical person can install and understand. Use descriptive names and short comments for decisions that are not obvious from the code. Add a docstring to a new public function explaining its behavior and important side effects; avoid comments that merely repeat a line of code. Keep user-facing wording plain and test it at the minimum supported window size.

Start with [ARCHITECTURE.md](ARCHITECTURE.md) for the process and file map. Most app changes are in `long_tasks.py`; setup changes are in `Setup.ps1` and `Install-Backend.ps1`. Do not commit installed runtimes, `Cloud/`, `LongTasks/`, user `Projects/`, logs, or account tokens. Generated weights are excluded except reviewed safe JSON specialist candidates under `ModelContributions/<experiment-sha256>/`, with pinned public-data provenance and held-out evaluation. These candidates are not runtime payloads, must not enter `install-files.json`, and never imply activation. Do not include raw datasets or private data. `install-files.json` is the release allowlist.

For development, install Ruff with `python -m pip install ruff`, then run `python -m ruff format .`, `python -m ruff check .`, and the relevant `Validation/test_*.py` files. The app does not require Ruff to run. Media checks use `Media/python/Scripts/python.exe` and require downloaded media weights. Parse PowerShell scripts before packaging, run `build-release.ps1`, and inspect the ZIP for the intended files and any secrets. Run the desktop app to check layout and real mouse-wheel behavior for UI changes. A passing unit test does not replace a fresh-install test when installation logic changes.

The installed Astro kit occupies one manifest entry. After changing its vendored
sources, run `python pack-release.py --refresh-astro-kit .` and commit the refreshed
`vendor/ai-ui.zip` with those sources.

New account integrations must keep per-user credentials private, verify callback state and token identity, and make use of any shared or paid allowance an explicit user choice. Model changes must state realistic RAM and disk requirements and preserve local fallback.

Idle AI contributions use the maintainer-owned `donation-tasks.json` queue and the contributor's explicitly selected Local, Free cloud, or ChatGPT resources. Each entry names a small set of public source/test files. Keep the combined source below 40,000 characters and assign a concrete area for a demonstrable fix, not generic churn. Contributions arrive as `[Donation]` draft pull requests. Review the diff, confirm the claimed bug, run the regression test and appropriate existing checks, and mark the draft ready only when it merits acceptance. Generated proposals are never automatically merged or executed on contributors' machines. Do not widen their file scope to account credentials, workflows, installers, private files, or donation consent. The leaderboard awards credit only after an eligible contribution is merged into the canonical repository; tokens and unmerged proposals do not earn points.

The explicit queue covers song vocal/style handling, audio edits, lyric timestamps, FFmpeg and managed-tool health, local-server recovery, context history, document caches, project memory, runtime error episodes, feedback, arithmetic and task timing. Each assignment fits the ordinary donation lane's source budget and includes an approved packaged regression-test file. Run `python -m pytest -q benchmarks/test_donation_catalog.py` after changing assignments; an oversized public module can otherwise fail before any model review begins. This developer check ships in the source archive and adds no runtime dependency.

Donation reports are proposed code changes submitted as draft pull requests. A review that finds no defensible fix records usage locally and submits nothing. Desktop runtime error episodes remain local in `LongTasks/runtime-issues.sqlite3`; these are not automatically uploaded crash reports. More review capacity can increase coverage, but cannot guarantee more distinct bugs or accepted fixes.

When a fix ships, maintainers can add the reviewed result to `donation-reviewed-scopes.json`. Set the job ID to the value returned by `donation.scope_fingerprint(job, blobs)`, using the job's actual instructions and the Git blob IDs for every file after the fix. Use the tested revision's Git tree to obtain those IDs. Donors skip only that exact scope before using model tokens. A change to an assigned file or instruction reopens the area for review.
